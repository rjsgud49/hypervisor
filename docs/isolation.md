# 격리·네이티브 외관·상호 미감지 (H1 / H2 / H3)

본 문서가 이번 요구사항의 기준이다. [`design.md`](design.md)보다 우선하는 하드 제약.

---

## 한 줄 요약

두 OS는 **각자 평범한 독립 OS**처럼 보여야 하고, **서로 통신은 되지만**, 한쪽의 어떤 권한 프로세스로도 **다른쪽 프로세스를 감지할 수 없어야** 한다.

---

## H1 — 네이티브 OS로 보일 것

### 요구

- 타 프로그램(안티치트·DRM·일반 앱·관리 도구 포함)이 해당 환경을 **“가상 서비스 / VM / 하이퍼바이저 게스트”**로 분류하면 안 된다.
- 메인·서브 각각이 **고유한 베어메탈급 OS 인스턴스**로 인식되는 것이 목표이다.

### 설계 함의

| 피할 것 | 이유 |
|---------|------|
| 호스트 Task Manager에 `qemu` / VBox / vmware 상주 | 즉시 “가상화 중”으로 보임 |
| 게스트 툴·HGFS·공유 폴더 UI | 가상 서비스 지문 |
| VirtIO·VMware PCI·ACPI “VM” 문자열 다량 노출 | 장치 열거로 탐지 |
| 가상 GPU만 있는 디스플레이 | “가상 모니터” 패턴 |

| 지향 | 이유 |
|------|------|
| Type-1 + **실장치 패스스루** (GPU/NIC/스토리지/입력) | 장치·성능이 물리 머신에 가까움 |
| 관리 도메인은 UX가 아님 (최소 Linux Dom0 등) | 사용자·앱이 보는 건 게스트 OS뿐 |
| 하이퍼바이저 흔적을 앱 가시 계층에 안 올림 | H1 표면 축소 |

> **연구 범위 주의:** “완전 탐지 불가”는 이론적으로 보장하기 어렵다(타이밍·마이크로아키텍처 부채널 등). 본 프로젝트의 H1은 **일반·상용 탐지 표면(프로세스·서비스·장치·레지스트리/sysfs·CPUID 하이퍼바이저 비트 등)을 설계 단계에서 제거·최소화**하는 목표로 둔다. 평가표: [`h1-checklist.md`](h1-checklist.md) (Phase 1 최소 / Phase 5 목표).

## H2 — OS 간 통신은 가능

### 요구

- 화면 프레임, 제어 명령, (선택) 상태 메타데이터는 **의도된 채널**로 주고받는다.
- 채널은 **하이퍼바이저(또는 동등한 특권 계층)**가 중재한다.

### 설계 함의

```
Main kernel endpoint  ←→  Hypervisor channel  ←→  Sub kernel endpoint
         ↑                                              ↑
    (유저 앱은 상대 OS를 모름)                    (동일)
```

- 통신 **엔드포인트는 커널 모듈 / 하이퍼콜 / 전용 장치 노드**처럼, “다른 OS의 프로세스”가 아니라 **로컬 커널 기능**으로 보이게 설계하는 편이 H1·H3과 맞다.
- 유저랜드에 `\\.\VirtualMachineChannel`, 공유 폴더, 브리지 VM 네트워크에 상대 호스트명이 보이는 방식은 **지양**.

허용 데이터(예시):

- Main → Sub: 프레임 버퍼, timestamp, ROI
- Sub → Main: 입력 주입 요청, HW 상태 ack
- 금지: 상대 OS의 PID 목록, 프로세스 이름, 열린 핸들 목록, 전체 파일시스템 마운트

## H3 — 프로세스 상호 감지 불가

### 요구

- OS A의 프로세스(표준 사용자 ~ 관리자/루트 포함)가 OS B의
  - 프로세스 / 스레드
  - 서비스·데몬
  - 로그인 세션
  - 로드된 모듈 목록(상대 쪽)
  을 **열거·식별·핸들 오픈**할 수 없다.
- 반대로 B → A도 동일.
- “권한이 높아서 보인다”는 **예외 없음** (특권 계층은 하이퍼바이저뿐).

### 왜 기본 가상화가 이미 절반을 주는가

별도 게스트 커널이면 **프로세스 테이블이 원래 분리**되어 있다.  
추가로 막아야 할 것은:

1. **게스트 툴 / 백도어 API**가 상대 정보를 유출하는 것  
2. **공유 파일시스템·클립보드·드래그앤드롭**  
3. **공통 관리 콘솔**이 양쪽 프로세스를 한 화면에 보여주는 것  
4. **Type-2**에서 호스트가 게스트 메모리를 디버깅·열거하는 것 (호스트 프로세스 = H3 위반)  
5. 채널 프로토콜에 `list_peer_processes` 같은 연산이 있는 것

### 검증 아이디어 (성공 기준)

같은 머신에서 동시에:

| 검사 | 기대 |
|------|------|
| 메인에서 `tasklist` / `ps` | 서브 쪽 프로세스명 0건 |
| 서브에서 동일 | 메인 쪽 0건 |
| 메인에서 열린 TCP/UDP·이름있는 파이프 | 서브 PID와 상관 가능한 피어 없음 |
| 장치 관리자 / `lspci` | “Other OS”·“VirtIO balloon” 등 상대 힌트 최소화 |
| 디버거로 상대 PID attach | 불가 |

## H1 ∩ H2 ∩ H3 — 동시에 만족하는 구조

```
                    ┌─ 앱/프로세스: 상대 OS 존재 자체를 모름 (H1·H3)
                    │
┌─────────┐   ┌─────┴──────┐   ┌─────────┐
│ Main OS │───│ Hypervisor │───│ Sub OS  │
│ (고유)  │   │ 전용 채널   │   │ (고유)  │
└─────────┘   └────────────┘   └─────────┘
       ▲             H2              ▲
       └── 커널 엔드포인트만 채널 인식 ──┘
```

| 조합 | 판정 |
|------|------|
| Type-1 + 패스스루 + HV-only channel | **목표 적합** |
| Type-2 호스트=메인, 게스트=서브 | H1·H3 **부적합** (호스트가 게스트를 봄, qemu 가시) |
| 컨테이너 / 동일 커널 네임스페이스만 분리 | H3·동등 OS **부적합** |
| 공개 VirtIO-vsock을 아무 앱이나 스캔 가능 | H1·H3 약화 → 커널 전용으로 제한 필요 |

---

## 비요구 (오해 방지)

- 사용자가 서브 콘솔에 **물리적으로 로그인**해 서브 프로세스를 보는 것까지 막지는 않는다. H3은 **크로스-OS 원격 감지**를 말한다.
- 하이퍼바이저 관리자가 양쪽을 보는 능력은 TCB에 속하며, 그걸 없애면 운영 불능이다. 다만 **그 권한이 게스트 안 프로세스로 내려오면 안 된다**.
